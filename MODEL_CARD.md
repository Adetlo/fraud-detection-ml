## Intended use

Educational fraud **risk scoring and decision support** on synthetic transactions: produce
a probability, a risk band (LOW / MEDIUM / HIGH / CRITICAL), a decision-support label
(PASS / REVIEW / PRIORITY_REVIEW) and reason codes for review prioritisation by a human or
a downstream control.

## Out-of-scope use

* Autonomous blocking or declining of transactions (there is no BLOCK output).
* Any decision about real customers, accounts or payments.
* Regulatory compliance, suspicious-activity reporting or audit evidence.
* Inputs whose history fields were not computed point-in-time, or that violate the contract.

## Training data

Synthetic, generated by `fraud_ml.data.synthetic` with seed 42: 50,000 transactions, 1,250
accounts, 2025-01-01 to 2025-06-30, seven currencies, seven channels, seven transaction
types. 501 fraud-labelled rows (1.00%) from ten stylised patterns mapped to five synthetic
types: CARD_NOT_PRESENT 195, ACCOUNT_TAKEOVER 137, MULE_ACTIVITY 101, STRUCTURING 50,
RAPID_MOVEMENT 18. Legitimate behaviour deliberately overlaps with fraud (legitimate large
payments, new beneficiaries, night-active accounts, travel, new phones). Training data hash
is recorded in the artifact metadata.

## Features

Transaction (amount in reference units, band, structuring proximity, categoricals),
temporal (hour, weekday, cyclic hour, unusual-hour score), velocity (1h/24h counts and
sums, distinct counterparties, inflow ratio) and behavioural (amount vs 30-day median and
mean, days since last, account age, new beneficiary/device, cross-border, dormant, new
account). No identifiers, labels or post-outcome fields. See
`docs/FEATURE_ENGINEERING.md`.

## Evaluation

Temporal split: train 35,000 rows (338 positives), validation 7,500 (96), test 7,500 (67).
Metrics at the selected threshold 0.065 (test split):

| Metric | Value |
|---|---:|
| PR-AUC | 0.757 |
| ROC-AUC | 0.992 |
| precision | 0.326 |
| recall | 0.836 |
| F1 | 0.469 |
| Brier score | 0.0041 |
| review rate | 2.29% |
| alerts per 1,000 | 22.9 |
| expected illustrative cost | 1,736 (231 per 1,000) |
| confusion (TP / FP / FN / TN) | 56 / 116 / 11 / 7,317 |

Baseline logistic regression on the same test split: PR-AUC 0.754, recall 0.925 at a 3.04%
review rate. The two are statistically indistinguishable on 67 positives; XGBoost was
selected on validation PR-AUC (0.786 vs 0.667) and review rate. Segment performance is
reported per currency, channel, transaction type and domestic/cross-border; this is not a
fairness analysis (no protected attributes exist).

## Threshold

Policy: recall >= 0.80 within a 5% review-rate ceiling, minimum illustrative cost
(FN 100, FP 5, TP 1). Selected on validation: threshold 0.065, priority threshold 0.41,
LOW upper bound 0.0325. Policy satisfied.

## Known limitations

* Synthetic data and synthetic labels; nothing here measures real fraud performance.
* Few positives: metrics carry roughly ±0.05 PR-AUC uncertainty; results vary by seed and
  the baseline wins outright at 10,000 rows.
* Cold-start history at the start of the window (every first counterparty is "new").
* Single-currency account statistics; static illustrative FX factors.
* No graph/network, device-fingerprint or merchant-risk features; no streaming features.
* Reason codes are rule-based indicators, not explanations of the model's prediction.
* No analyst feedback loop, no delayed-label evaluation, no automated retraining.

## Monitoring

PSI-based data drift on 21 input columns and score drift on `risk_probability`; score
distribution summaries; data-quality snapshots; structured request logs. Performance and
concept drift are not monitored (labels unavailable). See `docs/DRIFT.md`.

## Ethical and responsible use

The model supports review prioritisation only. Outputs must not be used to block, decline
or penalise anyone. The reason codes are designed to be read by a human reviewer and must
not be presented as proof of wrongdoing. No demographic or protected attributes are used,
and no fairness claim is made.

## Versioning

Artifacts are stored per training run with `model_version`, `run_id`, schema/feature/score
versions, training data hash, git commit, seed, library versions, configuration, policy,
metrics and the SHA-256 of the serialized pipeline. Loading fails safely on any version or
integrity mismatch. See `docs/MODEL_GOVERNANCE.md`.
